# Managed ChatGPT profile handoff

Kar can authorize a new ChatGPT connection on a helper machine and activate it on another Kar workbench. Each Codex instance retains independent registrations. Both endpoints require the owner bearer and a separate per-window `Kar-Auth-Client` secret. Keep both connections on trusted TLS or loopback. No ordinary chat, event journal or profile-list response receives the OAuth credentials.

## Client flow

Use `/projects/{project}/accounts/{instance}/chatgpt` on each workbench. A usable Codex instance comes from the default `codex` driver or the host's `KAR_AGENT_SESSION_CONFIG`.

1. On the destination, POST `/prepare` with `{}` to reconnect the active or last registration, `{"client_id":"oaiapp_…"}` for a particular saved registration, or `{"different_account":true}` for a new account. The returned ten-minute transfer ticket carries the destination's temporary X25519 public key and OIDC nonce. The private key stays on the destination. Pass the body directly to the authenticated helper over the trusted client connection. Keep the ticket out of URLs, telemetry and persistent browser storage.
2. On the helper, POST that body to `/handoffs`. Open `state.authorization_url` in a browser and subscribe to `GET /handoffs/{flow}` using the same client credentials. The helper listens on the exact assigned IPv4 loopback callback port. A remote browser can deliver its exact returned URL by posting `{"callback_url":"…"}` to `/handoffs/{flow}/callback` from the initiating client. DELETE `/handoffs/{flow}` cancels the flow. A subscriber that reconnects receives the latest status including a finished result while the ticket remains valid.
3. Send the finished event's `offer` and encrypted `profile` to destination `POST /import` from the window that prepared it. Replaying a completed import with the same body returns its receipt while the ticket remains active. After a process restart query `GET /profiles` for the durable registration. An interrupted, unfinished handoff requires a fresh ticket.
4. The destination validates the issuing service, JWKS signature (RS256 or ES256), expiry, client audience and authorized party, signed subject/email, transferred scope and account binding. The helper verifies the callback state, exact redirect, PKCE S256 and ID-token nonce. Both check signed access-token hashes where provided. A failed validation keeps the prior connection. Successful replacement releases native chats using the credential binding. The helper discards the transient credential at the end of authorization.

The destination protects credentials at rest with AES-256-GCM and a private per-instance key. An active managed chat uses Codex's native `openai_token_sharing` Responses provider and `auth.command`. The hidden Rust helper returns its token on the native command pipe. Its invocation contains the instance directory and an identity revision. Reconnection invalidates prior revisions. Refresh respects expiry, earliest refresh time and rotation, and serializes the token exchange. Normal logout clears local tokens, attempts native revocation and reports whether the issuer confirmed it. The registration remains available for reconnection. A signed-out managed instance requires reconnection before launching new chats. Managed token sharing has no native reset-credit identity.

## Host and verification

Production uses OpenAI's fixed HTTPS OIDC issuer, the native dynamic agent registration and the `chatgpt.tokens.use.direct` consent scope. Availability requires a participating ChatGPT account and a Codex executable supporting `model_providers.*.auth.command` and the Responses provider. An embedded Rust host can set `KAR_CHATGPT_HELPER_BIN` to the absolute Kar executable. A standalone Kar workbench invokes itself. Protect the Kar state directory and its private key within the OS account. The helper and destination may use different workspaces, native homes and owner credentials.

The loopback issuer override `KAR_CHATGPT_LOOPBACK_ISSUER` accepts only a local HTTP IP origin with an explicit port and is intended for isolated development fixtures. HTTPS production discovery pins every endpoint to the expected issuer and disables redirects.
