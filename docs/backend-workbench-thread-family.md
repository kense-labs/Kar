# Side chats and chat deletion

A project owner can start a side chat through `POST /projects/{project}/chats/{parent}/forks`. Send `id`, `turn` (a completed parent turn) and `side_chat: true`. Omitting `turn` selects the latest completed turn or starts a fresh side chat when the parent has none. The selected origin stays fixed on retry. Kar forks the conversation at that turn in the parent's current checkout. It leaves current files in place. The child has its own input queue and native context or the requested supported portable fallback. Project chat metadata exposes `side_chat_parent`. Normal forks have independent lifecycles. A side chat must stay in the same project and cannot itself be started by a side chat or delegated task.

`PUT /projects/{project}/chats/{parent}/archive` with `{"archived":true}` archives the parent's live side chats and closes their local controllers. A side chat waiting for delegated work stays active. Restoring the parent also restores children archived with it. A side chat archived before the parent keeps its previous state. Archive and deletion changes appear in the project thread metadata event feed.

`DELETE /projects/{project}/chats/{chat}` accepts a JSON body with a fresh `command_id` and optional `only_if_unused` (also `commandId` and `onlyIfUnused`). The receipt's `deleted` list names the affected chats. A conditional close returns an empty list when the selected chat already has its own input, run or pending delivery. An inherited prefix by itself leaves a side chat eligible. The same command and request return the saved result after a lost reply or restart. Reusing a deleted chat UUID to create, import, or fork is rejected.

Kar returns HTTP 409 for unconditional deletion if a member is running, has unresolved input or on-going workspace recovery, or another process owns its session. Resolve or withdraw pending work and retry the command. The fixed upstream implementation can cancel active runs as part of deletion. Kar uses its established queue/stop controls so that this command cannot silently discard an input whose delivery is uncertain.

Deletion covers the parent and its side chats in one catalog transaction. The service fences controller acquisition and input admission, closes idle owned sessions, records a command receipt and tombstones, and finishes private storage cleanup. Startup retries interrupted cleanup. Local checkout contents and native provider account history belong to their respective owners. An ordinary fork retains access to its inherited turn evidence, attachment blobs and shared Git objects. While any surviving fork depends on a deleted ancestor, Kar retains that ancestor's journal and associated blobs as private fork evidence. The last dependent chat's deletion releases them.

## Verification

`cargo test --locked --test chat_restart -- workbench-thread-family` uses two HTTP clients, an isolated Kar service and Git workspace, and a local Codex protocol peer. It exercises a pending input, conditional no-op replay, a live run, same-project constraints, independent archive state, parent deletion, retry after restart, UUID reservation, and a subsequent fork from inherited history. The command is registered in the workbench suite for consolidated execution. Development verification uses `cargo check --locked --all-targets` on macOS. The fixture does not call a provider account.
